Implement merge sort in Python and test it on a random list. Use a list data structure implemented in Assignment 2. Measure the runtime for growing input sizes and compare it with the theoretical O(n log n) bound.

## Use singly linked list
- Reason: one pointer per node, less memory than a doubly linked list. Although its append walks the whole list (O(n)), but I let merge to keep its own reference to the last node of the result, so each element is added in O(1), merge runs in O(m + n), and the whole sort in O(n log n).

## Runtime measurement

| n | time (s) | time / (n log₂ n) [ns] |
|---|---|---|
| 1000  | 0.0037 | 374.8 |
| 2000  | 0.0080 | 362.9 |
| 4000  | 0.0166 | 347.5 |
| 8000  | 0.0361 | 348.4 |
| 16000 | 0.0823 | 368.1 |
| 32000 | 0.1899 | 396.5 |

If the runtime is c · n log n, then time / (n log n) should stay roughly constant. It stays between about 350 and 400 ns while n grows 32 times, so the measurements match the theoretical O(n log n) bound.

When n doubles, the time grows by a factor of about 2.1–2.3, close to the expected 2·log(2n)/log(n) ≈ 2.15 for n log n, and far from the factor 4 of an O(n²) algorithm. The small increase for the largest n is likely due to cache effects (nodes spread out in memory), which changes the constant c, not the growth rate.

## Compare the memory consumption and the runtime of addEdge and removeNode with an adjacency list implementation

Let V be the number of nodes and E the number of edges.
For the adjacency list, I assume the standard implementation from the slides: each node has a list of (neighbour, weight) pairs.

| Operation   | Adjacency matrix | Adjacency list |
|-------------|------------------|----------------|
| Memory      | O(V²)            | O(V + E)       |
| addEdge     | O(1)             | O(1)           |
| removeNode  | O(V²)            | O(V + E)       |

### Memory
The matrix stores one cell for every pair of nodes, whether or not an edge exists, so it always uses V² cells. The adjacency list stores one list per
node and one entry per edge, so it uses V + E.

### addEdge
Matrix: the dictionary gives the row and column of u and v in O(1), and setting M[i][j] = w is O(1). Total O(1).
List: appending (v, w) to the list of u is O(1).
Both representations are equally fast for addEdge.

### removeNode
Matrix: removing row i is O(V). Removing column i means calling pop(i) on each of the V remaining rows, and each pop shifts up to V elements, so this
is O(V²). Re-indexing the nodes after u is O(V). Total O(V²).
List: deleting u's own list removes all outgoing edges. To remove the incoming edges, every other node's list must be scanned, which touches all
V lists and all E edges. Total O(V + E).
The list is faster for removeNode unless the graph is very dense(E close to V²), in which case both are O(V²)

### Which representation to choose
- Sparse graphs (E much smaller than V²): use an adjacency list. It needs far less memory and removeNode is faster. Most real-world graphs, such as
  road or social networks, are sparse.
- Dense graphs (E close to V²): an adjacency matrix is a good choice. The V² memory is used anyway, and it can check whether an edge exists in O(1),
  while a list needs O(degree).
- Graphs where nodes are added and removed often: use an adjacency list, because removeNode on a matrix is O(V²).
- Small graphs, or algorithms that check many individual edges: a matrix is simple and fast.


# Task 3
Implement a function BFS(G,v,...) that searches for a node u in a graph G using breadth first search and additionally returns the number of edges on the shortest path from v to u. Provide an example to test this function and explain why depth first search cannot be used for that purpose.

## explain why depth first search cannot be used for finding shortest path
BFS uses a queue (FIFO), so it explores the graph level by level: first all nodes 1 edge away from v, then all nodes 2 edges away, and so on. The first
time BFS reaches u, it has used the fewest possible edges.

DFS uses a stack (recursion) and follows one path as deep as possible before backtracking. The first path it finds to u is not necessarily the shortest,and once u is marked as visited, DFS never revisits it through a shorter path.
