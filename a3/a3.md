## Task 2: Binary tree with four traversals

Implement a binary tree in Python and provide pre-order, in-order, post-order and level-order traversals. Give the runtime of each traversal and explain which additional data structure the level-order traversal needs.


### Design

The node class `BTree` follows slide (`key`, `parent`, `left`, `right`). There is no separate tree class; the tree is represented by its root node.

Note on this design: an operation is called on a node object, so an empty tree (no root node) cannot call any method. The caller must check `if root is not None` before traversing. For the same reason, removing the last remaining node is not supported.

### Runtime of each traversal

| traversal | runtime | reason |
|---|---|---|
| pre-order | O(n) | every node is visited once, O(1) work per node |
| in-order | O(n) | same calls as pre-order, only the print position differs |
| post-order | O(n) | same as above |
| level-order | O(n) | every node is enqueued once and dequeued once, both O(1) |


### Additional data structure for level-order: a queue

Level-order visits the tree level by level: first the root, then all nodes at depth 1, then depth 2, and so on. This needs a **queue** (FIFO):

1. Put the root into the queue.
2. While the queue is not empty: take the node at the front, visit it, and add its children at the back.

Because children are always added at the back, all nodes of one level leave the queue before any node of the next level. A stack (LIFO) would instead always take the most recently added child and go deep first, which gives a depth-first order.

The queue is `collections.deque` (recommended in slides). `append` and `popleft` are both O(1). A normal Python list with `pop(0)` would shift all remaining elements on every dequeue (O(n)), making level-order O(n²) in total.

## Task 3: Stack and Queue on top of the lists from Assignment 2

Implement a Stack and a Queue in Python on top of the list data structure you already implemented. Give the runtime of every operation and explain which underlying representation you chose for each of the two ADTs and why.

### Stack: singly linked list (`LinkedList`, A2 Task 2)

The head of the list is the top of the stack.

**Why:** a stack only ever works at one end. Push, pop and top all touch the head, which a singly linked list reaches in O(1). A doubly linked list would also work, but its extra `prev` pointers are never used here and only cost memory.

The top must be the **head**, not the tail: our singly linked list has no tail pointer, so adding at the back (`append`) walks the whole list, O(n).

| operation | implementation | runtime |
|---|---|---|
| `__init__` | create an empty `LinkedList` | O(1) |
| `push(v)` | new node becomes the head | O(1) |
| `pop()` | `LinkedList.delete(top value)`, which removes the head in its first branch without looping | O(1) |
| `top()` | read the head's value, `None` if empty | O(1) |
| `empty()` | `LinkedList.empty()` | O(1) |

### Queue: singly linked list (`LinkedList`, A2 Task 2)

Enqueue at the tail, dequeue at the head (as slides show).

**Why a singly linked list:** a queue is FIFO, so it needs fast access to **both** ends: one to add, one to remove. A singly linked list gives O(1) at both ends as long as there is also a reference to the last node:
 
- **enqueue at the tail:** the old tail's `nxt` points to the new node, then `tail` moves to the new node. No loop, O(1).
- **dequeue at the head:** the head moves to the next node. No loop, O(1).
This works because a queue **never removes at the tail**. Removing the last node is the one operation a singly linked list cannot do in O(1): without `prev` pointers, finding the second-to-last node means walking from the head.
 
**Why not the doubly linked list:** it would also give O(1) for every queue operation, but each node stores an extra `prev` pointer that the queue never uses. The singly linked list needs only one pointer per node, so it uses **less memory** for the same runtime.

**About the direction:** the Queue ADT only requires FIFO, elements enter at one end and leave at the other. Which end of the list is the front is an implementation choice. With a singly linked list, only one direction is fast:
 
| singly linked list + tail | enqueue | dequeue |
|---|---|---|
| add at tail, remove at head (chosen) | O(1) | O(1) |
| add at head, remove at tail | O(1) | O(n), removing the tail needs the second-to-last node |
 
Both directions give a correct queue, but only the chosen one keeps both operations O(1). A doubly linked list would be O(1) in both directions, because `tail.prev` gives the second-to-last node directly.
 
**When the doubly linked list would be the better choice:**
 
- if removal at **both** ends were needed (a double-ended queue, *deque*), since removing the tail must then be O(1)
- if the goal is to reuse an existing list class without managing a tail reference in the Queue

Neither applies to a plain queue, so the singly linked list with a tail reference gives the same runtime with less memory.
 
**Implementation notes:** the `LinkedList` class from my A2 has no tail, so the Queue stores the tail reference (`self.tail`) itself:
 
- `LinkedList.append` is not used for enqueue, because it walks the whole list (O(n)) and does not update the Queue's tail. The Queue attaches the new node at the tail directly.
- When a dequeue makes the queue empty, `tail` is reset to `None`. Otherwise it would still point to the removed node, and the next enqueue would attach the new node to a node that is no longer in the list.
- `LinkedList.__len__` walks the whole list (O(n)), so the Queue keeps its own `size` counter to make `count()` O(1).


| operation | implementation | runtime |
|---|---|---|
| `__init__` | empty `LinkedList`, `tail = None`, `size = 0` | O(1) |
| `enqueue(v)` | attach a new node after the tail, move the tail | O(1) |
| `dequeue()` | `None` if empty, otherwise remove the head and return its value; reset `tail` if the queue becomes empty | O(1) |
| `empty()` | `LinkedList.empty()` | O(1) |
| `count()` | own size counter | O(1) |
